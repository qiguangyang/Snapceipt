# Snapceipt — Pre-Submission Security, UX & App Store Readiness Report
_Date: 2026-06-21 · Branch: `main` · Method: 19-dimension fan-out audit + adversarial verification (51 agents)_

All findings below have been adversarially verified against the source. Counts after dedupe: **0 critical · 4 high · 14 medium · 22 low/info**. There are no remote auth bypasses or cross-user data leaks. The blockers to submission are a small set of App Store guideline issues plus one payment-bypass bug.

## 1. Security

## SUBMISSION BLOCKERS (must fix before submit)

No criticals, but the following are must-fix (certain/high-likelihood App Store rejection, or a live payment bypass):

- [ ] **A1 — Privacy Policy unreachable in-app** (5.1.1) — add in-app `/privacy` link. _(High, certain rejection)_
- [ ] **A2 — Placeholder/fake UI in Release**, esp. the fake GPS toggle + dead chips (2.1) — delete or `#if DEBUG`-gate.
- [ ] **A3 — Dev diagnostic line ("…stub…") visible in Release** (2.1) — DEBUG-gate.
- [ ] **A4 — Paywall missing auto-renewal disclosure** (3.1.2) — add disclosure copy.
- [ ] **A5 — Unused `remote-notification` background mode** (2.5.4) — remove the entry.
- [ ] **A8 (account) — Reviewer cannot get past the login wall** — provide demo Apple ID / review inbox + OTP steps in ASC. _(Operational, not code.)_
- [ ] **S1 — Expired/revoked StoreKit txn still grants Pro** — add expiry/revocation rejection in `recordPurchase`. _(High; payment bypass.)_
- [ ] **S8 — Delete Account leaves local financial data on disk** — promote the wipe out of `#if DEBUG`. _(Privacy liability.)_

**Strongly recommended before relying on email-in in production (can ship gated):** S2/S3 (inbound email cost + sender verification).

---

## Verdict: NO-GO (until blockers cleared) — then GO

The backend has no remote auth bypass and no cross-user data leak; verified IDOR-class findings all re-scope by `userId` at read time, so user data is not exposed. The codebase is fundamentally sound and most findings are low/defense-in-depth. But the app cannot be submitted as-is: **A1** is a near-certain 5.1.1 rejection, and **A2/A3/A4/A5** are concrete 2.1/2.5.4/3.1.2 risks that are cheap to fix. **S1** is a live payment bypass that should not ship in a monetized app, and **S8** contradicts the "delete my data" action. All eight blockers are small, well-scoped, low-risk edits. Clear the checklist and the app is **GO**; remaining medium/low items (Dynamic Type, VoiceOver, contrast, email-in hardening, design-token cleanup) are strong fast-follows that do not gate launch.
