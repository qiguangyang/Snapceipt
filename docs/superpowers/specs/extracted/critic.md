# Completeness Critic

## Gaps
- AUTH/ONBOARDING SCREEN MISSING ENTIRELY. The screen inventory lists 'auth/onboarding' but neither the union summary nor shell.jsx (/Users/yangqi/Documents/github/Snapceipt/design-ref/snapceipt/project/app/shell.jsx) contains any sign-in, magic-link, Apple-button, splash, account-creation, or first-run/empty-account onboarding screen. The backend specs define Sign in with Apple + magic-link auth, but there is ZERO UI design for: the sign-in screen, the 'check your email' magic-link waiting state, the universal-link landing/verify state, sign-in error/expired-link states, and the cold-start onboarding (first profile creation, permissions priming for camera/notifications). This is a whole flow with no spec.
- BUDGETS ARE DISPLAY-ONLY DESPITE BEING 'REAL IN V1'. Decisions say 'Build REAL in v1: budgets + push alerts.' But the Personal budgets card 'Edit' link in home.jsx (line 361) has NO onClick handler, and the Business 'Deductible' card has no editor either. There is NO budget-creation/edit screen, no per-category cap setter, no budget-period config, no 'add a budget' flow, no budget detail. The entire budget management surface is unspecified. The backend has a budgets table but there is no UI to CRUD it.
- PUSH-ALERT CONFIGURATION & PERMISSION UX MISSING. 'Push alerts' are REAL in v1, but there is no design for: the APNs permission-priming/request screen, notification preferences (which alert types are push vs in-app, per-category budget thresholds, quiet hours), the deep-link target when a push is tapped (does it open AlertsSheet? the relevant transaction?), or the mapping between the static in-app AlertsSheet items and actual push triggers. AlertsSheet (shell.jsx lines 58-90) is a hardcoded read-only list with no per-item tap action, no read/unread persistence, no empty state, no mark-all-read, and no clear/dismiss.
- TRANSACTION EDIT SCREEN MISSING. TxnDetail has an 'Edit' button (transactions.jsx line 182) and a 'Delete' button (line 185) but NO edit form/screen is designed. Editing a transaction (changing category, amount, merchant, GST, deductible %, mode/profile reassignment, attached receipt) is core to a receipt app and to local-first sync, yet entirely unspecified. Delete also has no confirmation dialog and no undo design despite soft-delete tombstones in the backend.
- CAPTURE REVIEW-STEP FIELD EDITING IS UNSPECIFIED. The decisions and the ReceiptScanner.swift contract both stress 'Always let the user verify before saving — OCR is never 100%,' yet in capture.jsx the ReviewStep renders fields via a static field() helper (e.g. field('Date','28 May 2026'), line 201), the edit button (line 166) has no handler, and the Category row chevron (line 211) has no destination. There is no field-edit UI, no category picker invoked from review, no date picker, no merchant text edit, no GST/deductible edit, and no low-confidence/needsReview variant UI (the summary admits the <high-confidence and missing-field states are 'NOT in prototype'). The single most important screen for OCR trust is under-specified.
- AddManual KEYPAD FLOW INCOMPLETE: date is hardcoded 'Today · 30 May 2026' (manual-page.jsx line 97) with no date picker; income mode shows only a single fixed 'income' chip with no category/source taxonomy; no GST/tax-deductible entry; no profile/mode selector (mode is inherited from active profile only, so you cannot manually add a Business expense while a Personal profile is active without first switching). No attach-receipt option from manual entry.
- CREATEQUOTE IS A NON-FUNCTIONAL SHELL. The bill-to client Card has a chevron affordance but NO client picker/CRM screen exists; line items are display-only (no inline editor for description/qty/price — confirmed in summary); 'Add' inserts a $0 placeholder row that cannot be edited; there is no quote-number authority UI, no saved-clients store, no quote list/history screen, no draft state, and no 'send' recipient/email selection. The whole quote feature is one editor screen with no supporting data screens.
- EMAIL-IN RECEIPTS HAVE NO IN-APP SURFACE. The decisions make email-in receipts a real v1 path (Email Routing -> Workers AI OCR -> DeepSeek), but there is NO UI for: displaying the user's personal inbound email address (so they can give it to merchants), copy/share/rotate that address, a settings row to manage it, a 'review email-in receipt' inbox/queue, or notification when an email receipt arrives and needs review. The backend open question about per-user alias vs shared address has no UI to expose either.
- SEND-TO-ACCOUNTANT / EXPORT RECIPIENT FLOW INCOMPLETE. ExportSheet generates a PDF/CSV/'accountant package' but there is no recipient-entry UI (accountant email address book), no send-history/'sent' confirmation screen, no re-share action for expired presigned links (a backend risk flags 7-day link expiry), no date-range/profile-scope selector beyond the period segment, and no in-progress/success/error states for the actual generate+email call.
- LOYALTY BARCODE: NO SYMBOLOGY CAPTURE. Barcodes are 'REAL in v1' but AddLoyaltyScreen only captures a free-text number (loyalty-page.jsx line 142) and the prototype barcode is faux stripes. There is no field to capture or detect the barcode SYMBOLOGY (Code-128 vs EAN-13 vs QR vs Aztec — these differ per retailer and cannot all be generated from a bare number), no scan-to-detect-format flow (the 'Scan card barcode' CTA has no defined output schema), and no barcode-generation-failure fallback UI is designed (summary notes it as a v1 to-do but it is not specified). The data model loyalty_cards.number has no 'format/symbology' column.
- PLACEHOLDER SCREENS LACK 'PLACEHOLDER' UX. Mileage GPS auto-track, ConnectedBanks, and the capture 'Add to mileage'/'Match to bank' chips are decided as placeholders, but they render as fully-functional-looking UI (toggles that move, 'Synced 2h ago' healthy states, connect buttons). There is no design for the disabled/'coming soon' affordance, no copy explaining the feature is not live, and the 'Add a trip'/'Log hours' CTAs and bank toggles have no defined no-op/placeholder behavior. A user will tap these expecting them to work.
- NO GLOBAL EMPTY / FIRST-RUN STATES. Multiple screens explicitly lack empty states (Home recent list, Loyalty wallet, Mileage trips, WFH days, quote with zero items, Categories with zero rules). For a brand-new account every screen is empty on day one, yet the union summary repeatedly notes 'no empty state implemented — rebuild should add.' The first-session experience (no profiles beyond default, no txns, no cards, no budgets) is entirely undesigned.
- SYNC / OFFLINE / ERROR UI IS UNSPECIFIED APP-WIDE. Local-first sync is a core decision, but there is NO design for: a sync-status indicator, offline banner, 'pending upload' badge on queued mutations, the 'updated elsewhere'/LWW-conflict toast referenced in backend risks, extract-failure retry UI on capture, send-failure retry on export/quote, or a global error/toast system. Every screen's 'Error' state is admitted as 'none in prototype.'
- PROFILE IDENTITY IS HARDCODED & ACCOUNT MANAGEMENT IS THIN. ProfileScreen identity block (MR / Maya Reyes / maya@studionorth.co / Pro) is hardcoded and does not reflect the signed-in user (confirmed in summary). There is no account-settings screen (change email, manage devices/sessions per the devices table, delete account, subscription/'Pro' management/paywall), and 'Sign out' has no confirmation or post-sign-out destination (ties back to the missing auth flow). Settings rows 'Export & backup', 'Privacy & security', 'Help & support', 'Notifications & alerts' toggle have no destination screens designed.
- MONTH PICKER / PERIOD SCOPE IS LOCAL & INCONSISTENT. Activity has a month picker but Reports has a Month/Quarter/FY segment and ExportSheet has its own period — there is no shared global period model, no custom date-range picker anywhere, and no FY boundary handling UI (AU FY = 1 Jul–30 Jun, critical for tax features but never surfaced as a selectable scope).

## Contradictions
- 'REVIEW/EDIT AI-EXTRACTED FIELDS' vs DISPLAY-ONLY REVIEW. The purpose statement for CaptureFlow says users 'review/edit AI-extracted fields,' and ReceiptScanner.swift's ReviewReceiptForm uses editable TextField/DatePicker bindings, but the actual capture.jsx ReviewStep renders non-editable static text via field() and the edit button has no handler. The spec promises editing the prototype does not implement.
- 'BUILD REAL IN V1: BUDGETS' vs NO BUDGET EDITOR. The decision says budgets are real, but the only budget UI is a hardcoded display card whose 'Edit' link is inert (home.jsx line 361). 'Real budgets' with a backend budgets table contradicts the complete absence of any budget create/edit screen.
- MODE IS DERIVED FROM ACTIVE PROFILE vs PER-TRANSACTION MODE. shell.jsx sets mode = active.type and TransactionsScreen filters txns by the active profile's mode, but TxnDetail and AddManual carry a per-transaction mode, and the capture ModeToggle lets you assign a receipt to Personal/Business independent of the active profile. This is contradictory: if a transaction's mode can differ from its profile, then filtering the ledger purely by active-profile type will HIDE transactions, and 'each profile keeps its own receipts' conflicts with a single shared txns array keyed only by mode (not by profile id). The data model uses profile_id on transactions, but the UI logic keys off type/mode — these two identity schemes collide for users with multiple business profiles (Studio/Lumen/Rentals all type='business' would share one ledger view).
- TAX_SETTINGS PER-PROFILE vs PERSONAL HAS NO GST. The data model has one tax_settings row per profile regardless of type (flagged as an open question), but ProfileDetail initializes GST=false and hides ABN/GST for personal, and TaxScreen is 'inherently business-oriented but renders statically regardless of mode.' If TaxScreen is reachable from a Personal profile's settings (it is, via the Profile hub), it will show ABN/BAS/entity-type fields that contradict the personal profile having no tax identity.
- GST INFERENCE round(total/11) vs MIXED-BASKET / GST-FREE ITEMS. The extraction pipeline infers GST as total/11 assuming a fully taxable supply, but AU supermarkets (Woolworths Metro, in the seed data) sell GST-free fresh food mixed with taxable items. The seeded Personal data leads with grocery merchants, so the inferred-GST default will be systematically wrong for exactly the most common personal receipts — contradicting 'ATO-grade' tax accuracy implied by the deductible/BAS features.
- MULTI-CURRENCY SCHEMA vs AUD-ONLY ROLLUPS. ReceiptScanner.swift and the D1 schema store per-row ISO-4217 currency (and OCR sniffs USD/CNY/GBP/EUR), but every aggregate (SummaryCard, budgets, GST, reports, export math) assumes AUD with no FX conversion. A captured USD/CNY receipt would corrupt totals. Decisions say 'Currency AUD' but the capture/storage layer accepts and stores foreign currencies with no reconciliation.
- ALERTS ARE IN-APP ONLY vs PUSH ALERTS ARE REAL. Decisions say 'NO emailed reminders (Alerts stay in-app)' AND 'budgets + push alerts' are real. A push notification IS an out-of-app surface. The spec must reconcile: budget alerts fire as APNs push (out of app) but then land where? The static AlertsSheet has no linkage to push, and there is no statement of which events push vs stay purely in-app. 'Alerts stay in-app' superficially contradicts 'push alerts.'
- 'DROP THE TWEAKS PANEL' vs TWEAKS-DRIVEN BEHAVIOR. Decision says drop the design-only Tweaks panel, but shell.jsx wires real behavior through TWEAK_DEFAULTS: profileCount (2/3/4) controls how many profiles exist, palette tweaks define the Personal/Business accents, and toggleStyle/snapStyle/multiStyle select component variants used by Home/Profile. Dropping the panel without deciding fixed values for profileCount, the two default palettes, and which toggle/snap/multi variant ships leaves those production values unspecified.
- SNAP TAB ALWAYS OPENS CAMERA vs 'AMOUNT-FIRST MANUAL ENTRY' PROMINENCE. The raised-center Snap tab (shell.jsx line 200) always opens CaptureFlow (camera). Manual entry is only reachable via a Home QuickAction. For a user who wants to add income or a cash expense, the primary tab-bar action forces the camera. Not strictly contradictory but conflicts with the equal billing manual entry gets in the feature list.
- STARTUP PROFILE = PERSONAL vs IDENTITY = BUSINESS. The design-system file says 'Default startup profile = personal' (terracotta), but the hardcoded identity (Maya Reyes / maya@studionorth.co / Studio North active in the Profile screenshot) implies a business-first user. The seed/active-profile defaults are inconsistent across files (localStorage 'sc-active' default 'personal' vs screenshots showing Studio North active).

## Risks
- LWW SILENT DATA LOSS ON FINANCIAL RECORDS. Last-write-wins on updatedAt for transactions means concurrent offline edits to the same receipt on two devices silently drop one edit. For a tax/expense app this is higher-stakes than a typical app (a lost GST or deductible-% edit affects a BAS claim). The backend itself flags this; product must accept it explicitly and the 'updated elsewhere' toast is unspecified in the UI.
- PROFILE-vs-MODE IDENTITY COLLISION (see contradictions) is also a data-integrity RISK: with 3 business profiles sharing type='business', filtering ledgers/reports/budgets by mode rather than profile_id will commingle or hide transactions across distinct businesses, and budgets/tax_settings/quotes attributed to the wrong entity — a correctness bug that surfaces only for multi-business users.
- DEEPSEEK MODEL NAMING + JSON-MODE UNVERIFIED. 'deepseek-v4-flash' string, base URL, auth header, and whether it supports strict JSON schema vs only json_object are unconfirmed against the live API; JSON mode can return empty content requiring mandatory retry. A wrong model string or missing retry ladder causes intermittent extraction failures in the core capture flow. (Backend explicitly flags; reconfirm before coding.)
- WORKERS AI VISION OCR QUALITY ON EMAIL-IN PATH. llama-3.2-11b-vision-instruct is general-purpose, not a dedicated OCR engine, and its exact image input format (base64 vs byte array) and 256 default max_tokens (truncates long receipts) are under-documented. Email-in receipts may extract poorly with no on-device Vision fallback, and PDFs (common for emailed tax invoices) are not handled at all (no rasterization step).
- CLOUDFLARE EMAIL SENDING IS BETA. Email Send (magic-link, accountant export, the whole auth path) depends on a public-beta service with per-account enablement, verified-domain + SPF/DKIM/DMARC requirements, 25 MiB / 50-recipient / daily-quota caps, and binary-attachment behavior that cannot be tested with remote:true local dev. If beta access or deliverability fails, BOTH sign-in and exports break — auth is on the critical path with a single fragile dependency and no fallback provider chosen.
- SIGN IN WITH APPLE FIRST-RESPONSE DATA LOSS. Apple returns name/email only on first authorization; an app crash before persisting loses it irrecoverably with no re-fetch. Combined with the missing onboarding UI, there is no designed fallback to collect identity manually.
- BARCODE GENERATION FEASIBILITY. 'REAL' scannable barcodes require generating the correct symbology at sufficient resolution/quiet-zone for POS scanners; many loyalty programs use proprietary or QR/Aztec formats not derivable from a plain number. Without capturing symbology and a scan-to-detect path, generated barcodes may not scan at checkout — the feature could ship broken for a meaningful fraction of cards.
- TOMBSTONE & R2 GC NOT IMPLEMENTED = UNBOUNDED GROWTH. Soft-delete tombstones and processed_mutations grow forever unless the GC job (bounded by oldest device cursor) is built; delta pulls slow over time. R2 object reclamation must wait until all devices sync the delete or offline devices show broken receipt images. Neither GC job nor the 'min cursor across devices' tracking is specified as concrete work.
- ATO SUBSTANTIATION / RETENTION UNRESOLVED. AU tax substantiation may legally require retaining the original receipt image/PDF as evidence (and for ~5 years), but retention policy for R2 images, accountant-export PDFs, and tombstoned receipts is an open question. Eager deletion or short retention could destroy tax evidence; this is a compliance risk, not just a storage one.
- PRESIGNED-URL & INBOUND-TOKEN ABUSE. Accountant presigned links expire at 7 days (dead links for slow accountants); per-user inbound email tokens pasted into merchant forms can leak and invite OCR/AI cost abuse. Neither rate-limiting, token rotation, sender pinning, nor a revocable proxy-link design is specified in the UI/product layer.
- APNs SIGNING INSIDE WORKER. Budget push requires p8 auth-key JWT signing under Workers crypto; if the key handling or JWT signing fails, the 'real push alerts' feature silently does nothing. No fallback (in-app only) decision is documented for when push permission is denied — and permission-denied UX is undesigned.
- GST INFERENCE OVER-ESTIMATION (financial-accuracy risk): defaulting GST to total/11 on mixed/GST-free baskets over-claims input-tax credits, which is an ATO compliance exposure for the user, not just a UX nit. Inferred GST must be flagged for review, but the review screen that would surface that flag is itself under-specified.
- COLD-PULL PERFORMANCE AT SCALE. Multi-table delta pulls over D1/SQLite for large accounts (tens of thousands of txns + line_items + images) need (updatedAt,id) keyset indexes and pagination; unverified D1 query/row limits could make initial sync on a new device slow or fail. Local-first hides this until a big account installs on a second device.

## Recommendations
- Specify the entire AUTH + ONBOARDING flow as first-class screens: Sign in with Apple + magic-link entry, 'check your email' waiting state, universal-link verify/landing, expired/invalid-link error, camera+notification permission priming, and first-run profile creation. Decide magic-link strictness (same-device vs any-device) and the post-sign-out destination. This unblocks the rest, since identity, Pro status, and devices flow from it.
- Design the BUDGET management surface to honour 'real budgets': a budget list/editor reachable from the Home 'Edit' link and Profile, per-category caps, period (monthly + FY), over-cap threshold that drives push, and empty/first-budget states. Wire the budgets table to this UI.
- Add a NOTIFICATION/ALERTS system spec: APNs permission priming, a Notifications settings screen (per-type push vs in-app, budget thresholds, BAS reminders, quiet hours), push deep-link targets, and make AlertsSheet data-bound with read/unread persistence, per-item tap actions, dismiss, and an empty state. Explicitly enumerate which events are push vs in-app to resolve the 'no emailed reminders / push real' tension.
- Design the TRANSACTION EDIT screen and the CAPTURE REVIEW edit screen as one reusable editable form (mirror ReceiptScanner.swift's editable fields): merchant, date (picker), category (picker), amount, GST (with inferred-vs-printed flag), tax-deductible %, profile/mode reassignment, attach/replace receipt. Add a low-confidence/needsReview review variant and a delete-confirmation + undo (aligned to soft-delete tombstones).
- Resolve the PROFILE-vs-MODE identity model definitively: make profile_id (not type/mode) the partition key for ledgers, budgets, reports, tax_settings, and quotes; treat 'mode' purely as a display accent derived from the active profile's type. Re-spec TransactionsScreen/Reports/Home to filter by activeId, not by mode, so the 3 business profiles do not commingle. Update the union summary's mode-aware sections accordingly.
- Pin and verify external dependencies before build: exact DeepSeek model string + base URL + JSON-mode contract with mandatory validate+retry ladder; Workers AI vision image input format and raised max_tokens; Cloudflare Email Send beta enablement + verified domain + SPF/DKIM/DMARC, with a named fallback provider (Resend/Postmark) since auth depends on it; APNs p8 JWT signing under Workers crypto. Capture these as a pre-implementation checklist.
- Address AU tax correctness: prefer PRINTED GST over inferred total/11, flag inferred GST for review, handle mixed/GST-free baskets, and surface the flag in the review UI. Confirm ATO substantiation retention (likely keep original image/PDF ~5y) and write the R2 retention/lifecycle + tombstone-GC + min-device-cursor jobs into the backend scope explicitly.
- Lock currency scope: either constrain capture/storage to AUD (reject/convert foreign receipts at capture with explicit FX-at-capture handling) or design multi-currency rollups. Do not store foreign currency that aggregates silently mis-compute. Update ReceiptScanner default currencyCode from 'USD' to 'AUD' and the OCR sniff to bias AUD.
- Design the EMAIL-IN surface: show/copy/rotate the per-user inbound address (pick alias scheme), a review-queue for email-in receipts with extraction_status='failed' handling (still create a reviewable record so nothing is lost), and rate-limit/sender-pin controls. Design the ACCOUNTANT EXPORT recipient flow (address book, send history, re-share for expired links) and in-progress/success/error states for generate+email.
- Replace faux loyalty barcodes with a real plan: capture/detect symbology (Code-128/EAN-13/QR/Aztec) via the scan path, store a 'format' column on loyalty_cards, render with a vetted barcode library at scanner-grade resolution/quiet-zone, and design a number-only fallback when generation/format is unsupported. Add the wallet empty state.
- Give PLACEHOLDER features honest UX: mark GPS mileage auto-track, Connected Banks, and the capture 'Add to mileage'/'Match to bank' chips as visibly 'coming soon' (disabled or info sheet), with no live-looking sync states, and decide whether they hit a 501 endpoint or are fully client-stubbed (no network) to avoid misleading telemetry and user expectation.
- Add global cross-cutting UI: a sync-status/offline indicator, pending-upload badges on queued mutations, the LWW 'updated elsewhere' toast, a shared toast/error system, loading skeletons (sc-shimmer) on every list that reads from SwiftData/cloud, and first-run empty states for every screen (Home, Activity, Loyalty, Mileage, WFH, Categories, Reports donut, quotes). Treat day-one empty as a designed state, not an afterthought.
- Build out CreateQuote into a real feature: inline-editable line items (description/qty/price), a clients store + bill-to picker, server-authoritative quote numbering to avoid offline duplicate SN-#### , draft/saved states, a quote history list, send-recipient selection, and sending/error states. Or descope quotes to a clearly-labelled v1 stub if not core.
- Replace the dropped Tweaks panel with FIXED production decisions in the spec: confirm default profileCount behavior (dynamic add vs fixed), the two shipping palettes, and the single chosen toggleStyle/snapStyle/multiStyle/iconStyle variants — so removing the panel does not orphan those values. Make the signed-in identity data-bound (remove hardcoded Maya Reyes) and reconcile default active profile across files.
- Add account & settings depth: account settings (change email, manage devices/sessions from the devices table, delete account), Pro/subscription management or explicitly descope monetization for v1, and real destinations for Export/Privacy/Help rows. Add a shared period/date-range model across Activity, Reports, and Export, including AU FY (1 Jul–30 Jun) boundary handling and a custom range picker.
